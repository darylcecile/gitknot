# Durable events

The authoritative source is the core transactional `outbox`. Publishing to a Queue never removes the source. Source events and per-consumer receipts are retained for at least 30 days after commit, independently of Queue retention and dead-letter queues. All timestamps are RFC3339 UTC.

## Consumer contracts

`EVENTS` messages contain `{event_id,cell_id,shard_id}` and an optional consumer name. The source event is `EventRecord` from `@gitknot/core`; its ID, occurrence timestamp, actor, owning repository/account, resource revision, version, and data never change during retries or replay. The envelope selects the committed source database before any lookup. A missing declared source is retried, never acknowledged as completed. `webhooks`, `mail`, `index`, `meter`, and `operations` advance independently. Their effects and `processed_events` receipts share a database transaction. Queue acknowledgments follow durable effects or a durable retry deadline.

Effects resolve the current repository placement independently of the committed source. Fixed `operations.events` RPCs read source events and hand them to the current placement; `event_source_links` records their immutable identity. A handoff is complete only after the destination effect receipt exists. Old and new Queue copies therefore converge on the same delivery IDs and current authority.

Additional production bindings: `INDEX_EVENTS: Queue<{event_id}>`, `METER_EVENTS: Queue<{event_id}>`, `EMAIL` (Cloudflare Email Sending `send(EmailMessageBuilder)`), and `WEBHOOK_EGRESS: Fetcher` (the DNS-pinned HTTPS transport in `ops/egress`). The background entry point exports `OperationWorkflow` and the execution agent's `RunWorkflow`; its default export has `scheduled`, `queue`, and authenticated private `fetch` handlers only.

Public webhook events are thin, versioned records. Identity verification/recovery material, credentials, secret values, arbitrary provider responses, and stored email summaries are never included. Mail consumes identity events using current identity challenge/invitation records. Indexing rereads current authoritative resources, compares revisions, and writes the separate `SEARCH_DB`; stale/out-of-order events cannot restore deleted or hidden projections. Metering consumes source-ledger events, never operational telemetry.

Both Cron and `/internal/operations/sweep` enumerate every bounded local metadata shard. `identityAuthorityBindings(env)` preserves the identity binding and both physical descriptors before changing `DB` or `SHARD_ID`. Federation and financial sweeps run on the identity authority. Repository work validates current placement, and its D1 writes use the shared metadata-fence guard. Workflow runtime IDs include placement; public and external operation identities remain stable through movement.

Mail fan-out captures `mail_fanouts` / `mail_recipients` before materializing individual deliveries. Receipts are keyed by stable delivery identity, so changing inbox eligibility cannot shift a recipient into an already-processed numeric page. Activity mail rechecks current source policies, item/inbox revisions, recipient and preferences, suppression, and the exact send lease in its final release transaction. Only hashes enter its release audit.

### Cross-module wiring

- Core `outbox.created_at` comes from the database commit clock; `occurred_at` remains the immutable occurrence time. Replays persist their physical source and committed `through_rowid`, preserving membership after a shard move. Active replay ranges and pending consumers/deliveries pin source retention. A late projection of an old occurrence receives a full committed-source retention window.
- Billing: immutable chunks use `reserveStandaloneStorage` and verified `commitStorageObject`. `deleteStorageObject` owns physical deletion and financial settlement; Ops or the owning feature finalizes logical references, manifest state, repository-local quota and source events exactly once. `cancelStandaloneStorageIntent` tombstones provably unused intents, including ones with no reservation ID. Account quotas remain exclusively at the billing authority.
- `billing.storage.deletion_requested` is consumed through `claimStorageDeletion`. Ops owns archive/scan expiry and uses Core's `genericObjectDeletionMutation` and collaboration's `deleteAttachment` for those feature-owned finalizations. Unconfirmed owner cleanup remains durable pending work.
- Identity-mail preparation is API-only: register `registerInternalMailRoutes(app)` from `apps/api/src/modules/internal-mail.ts`. Background uses its private `API` service binding, exact scope `mail.prepare-identity`, and `POST /internal/mail/prepare-identity` with `{delivery_id,lease_token,shard_id}` immediately before `EMAIL.send`. The API rechecks the committed source, current send lease, action/invitation state, recipient, and authorization, then derives the token using its API-only identity key. It returns `{delivery_id,message}` transiently with `Cache-Control: no-store`. Only metadata and recipient hashes enter its preparation audit. Background must never receive `IDENTITY_KEYS_JSON`, `SESSION_KEY`, or a TOTP/master authentication key.
- Infra: the Email Sending binding permits `notifications@mail.gitknot.com` and `security@mail.gitknot.com` (staging uses `mail.staging.gitknot.com`). Status events require that sending-domain subscription and `MAIL_EVENT_ACCOUNT_ID`. `API` is required for identity mail. Execution snapshot cleanup also needs `BACKUP_BUCKET` bound to the execution snapshot bucket.
- Egress native implementation is `ops/egress/server.ts` + `transport.ts`. Infra's egress Worker/Container can point at this server; Docker build context is the repository root.
- Policy: `moving` must deny mutations while preserving authorized content reads; the directory keeps reads on the original cell until the epoch CAS. Every indirect object/collaboration write also needs this lifecycle fence.

Implementation details, exact table fields, private endpoints, retention, and verification commands are maintained here as the modules are integrated.
