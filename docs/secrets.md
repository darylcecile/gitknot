# Secrets, variables and the private vault

## Integration contract

Public API composition calls `registerSecretsRoutes(app)`. Management routes are `/v1/accounts/:accountId/{secrets,variables}`, `/v1/repos/:repoId/{secrets,variables}`, and `/v1/repos/:repoId/environments/:envId/{secrets,variables}`. Secret values are write-only. Metadata/version history is readable to secret managers; ordinary variables are readable configuration. `secrets.manage` never grants `secrets.use`.

Secret deletion is revocation with retained audit metadata. `DELETE .../secrets/:name` returns 204; the authorized single-resource GET continues to return 200 with the incremented `revision` and non-null `deleted_at`, without a secret value or ciphertext. Active lists omit the tombstone, and `/versions` retains immutable version metadata. A previously pinned runtime selection is denied by `deleted_at`; it cannot fall back to another scope or keep using the deleted version. A name that never existed, or an unauthorized scope, retains its normal not-found behavior. UI/E2E deletion checks should assert this tombstone/list/use-denial contract rather than require a 404 for retained metadata.

Precedence is environment → repository → owning organization/personal account → actor's personal account. Using a personal secret across account boundaries requires an explicit repository allowlist and cross-account policy; it is never an implicit way for an organization workflow to obtain a user's credentials. A plan pins exact names, immutable value versions, scope, and policy revision.

`@gitknot/secrets` server helpers use the private `SECRETS` service binding:

- `selectSecretsForPlan(env, input)` resolves declared per-step names into public metadata. Input includes the authenticated `principal`, `repo_id`, `workflow_id`, `commit_oid`, `ref`, `trust_class`, `executor`, `runner_pool_id`, `environment_id`, and `steps: [{step_id, secrets, variables}]`.
- `previewSecretsForPlan(env: SecretsClientBindings, input: PlanSelectionInput): Promise<PlanSelectionPreview>` calls authenticated `POST /internal/vault/preview` with `vault.plan`. It shares selection scope precedence, current authorization, names, versions, policy and size checks. The result is `{selection_digest,context,steps}` with every secret **and variable** `value` omitted, and its digest matches the executable selection for the same source. It issues no `vsel`, binds no plan, and performs no runtime resolution or decryption. Authorization/entry consistency is verified with SELECT-only primary probes; the normal signed-request anti-replay nonce is the sole write. A draft without a real workflow ID reports workflow-scoped vault constraints as unresolved rather than inventing an ID.
- `bindSecretPlan(env, {selection_id, plan_digest, principal})` immutably associates the selection with the final frozen plan digest. The digest must include the returned selection digest.
- `resolveAttemptSecrets(env, {attempt_id, generation, step_id, names})` returns only the requested, plan-declared values immediately before an authorized step. Keep that response in executor memory; redact before any Workflow checkpoint/log/snapshot. Never persist this call's return value in a Workflow step result.
- `revokeSecretVersion` and broker key rotation revoke or rewrap ciphertext without returning an existing value.

### Execution authority

Execution owns current attempts, frozen plans and environment approvals. The broker consumes **read-only D1 views**, so a signed caller cannot invent current authorization:

`secret_runtime_context` exposes one row per attempt: `attempt_id, generation, run_id, repo_id, account_id, actor_id, actor_kind, actor_user_id, actor_credential_id, workflow_id, plan_digest, selection_digest, commit_oid, ref, trust_class, executor, runner_pool_id, runner_id, runner_credential_generation, runner_credential_hash, environment_id, artifact_digest, destination, state, lease_expires_at, credentials_revoked_at, policy_revision, routing_epoch`. A usable state is `running`; the generation and unexpired lease must be current. `trust_class` must be `trusted`. The broker rechecks current identity/credential membership and `secrets.use` itself.

`secret_environment_authorizations` exposes `repo_id, environment_id, attempt_id, generation, plan_digest, commit_oid, artifact_digest, destination, policy_revision, approver_id, approver_credential_id, approver_mfa, approved_at, expires_at, revoked_at, current_commit_oid`. An environment-scoped release requires a current exact match and a currently authorized approver. A newer commit, changed policy, changed destination/artifact, revoked approver, expired approval or attempt cancellation denies release. Missing views fail closed. Environment/approval management remains owned by execution.

Execution persists immutable approving-credential/MFA evidence in migration 051 before creating the views in 059. The broker revalidates the original approving credential, its ancestors, current MFA and organization SSO; MFA is usable only when the original approval also recorded it. An approval without such evidence does not satisfy an MFA-required account policy. `current_commit_oid` represents the current accepted target, not merely the promotion's old commit.

Environment retirement uses migration 100's `workflow_environments.state`, `deleted_at` and `deleted_by`. Fresh vault writes, policy changes, executable selections, previews and runtime secret use require `state='active'` and `deleted_at IS NULL`. Authorized metadata/version history and secret/version revocation remain available for retired environments. A write captures its account-authority witness before its final active-environment read; the deletion operation's account barrier changes that epoch and rejects a late write atomically, including its ciphertext/version/audit batch. History access grants no runtime use.

Runner/pool metadata follows its typed locator's identity or repository authority. Principals and machine credentials remain on `IDENTITY_DB`. The runtime view has no shard-local runner join. `vaultMetadata` obtains the attempt/approval snapshot from the current repository shard, then uses execution's `loadRunnerAuthority` to validate the independently located runner/pool, current primary credential, exchange/retirement state and account epoch. It compares the attempt's original runner ID, credential hash and generation. The final use transaction includes execution's `identityRunnerPredicate` witness; metadata authority is enrolled in the same account barrier, so a rotation or trust change racing decryption cannot release plaintext. Fixtures verify valid releases for both locator authorities, stale original-hash/generation denials, and a final-transaction trust-change race without a runner replica.

### Broker bindings and scopes

Only `workers/secrets` receives `SECRETS_KEK_KEYRING_JSON` (a provider secret containing `{key_id: base64url_32_random_bytes}`) and `SECRETS_KEK_CURRENT_ID`. It also receives `DB`, `ENVIRONMENT` and `SECRETS_SERVICE_KEYS_JSON` (provider secret mapping each caller ID to its random signing key and explicit scopes). API/execution/background callers receive distinct `SECRETS_CLIENT_ID` and `SECRETS_CLIENT_KEY` bindings. The general `INTERNAL_SERVICE_KEY` is **not** a vault credential.

Signed requests bind client, method, path, purpose/scope, timestamp, nonce and exact body digest. The broker checks configured scopes and persistent replay protection before policy. API needs `vault.manage`/`vault.plan`; execution needs `vault.plan`/`vault.resolve`; a dedicated maintenance identity needs `vault.rotate`. The private worker has no public route or workers.dev exposure. There is no generic decrypt endpoint, including for operators.

Operations may use narrow `webhooks.manage` and `webhooks.sign` scopes: broker-generated 32-byte Standard Webhooks keys are shown once at creation/rotation; signing returns only `webhook-signature` for a currently authorized persisted delivery and exact body. Tenant vault resolve never handles webhook keys. No installation credential is returned by a generic decrypt operation; installation exchange requires its own resource-scoped broker operation.

The private Worker also mounts `handleFederationBrokerRequest` at `/internal/federation/*` before the ordinary vault router. It uses `SECRETS_FEDERATION_SERVICE_KEYS_JSON` with separate `federation.manage`, `federation.exchange`, `federation.sign`, and `federation.rotate` purposes. Enterprise client secrets and SAML signing keys remain encrypted in the federation vault tables; only protocol-specific exchange/sign operations can use them. A lazy KEK binding checks the shared active-key registry after federation authenticates its caller. Database guards fence late old-key writes across rolling deployments. Global KEK usage limits, recovery verification and retirement include federation ciphertext/wrap records. Revocation remains available while key writes are fenced. See `docs/federation.md` for the identity marker, trusted IdP origins and callback bindings; only the parent composition enables `FEDERATION_IDENTITY_CONTRACT=gitknot.identity.federation.v1` after installing its identity hooks.

## Encryption and provider boundaries

Every immutable version has a fresh random 256-bit data-encryption key and 96-bit AES-GCM nonce. A platform KEK wraps the DEK using a separate nonce and authenticated identity context. Account, scope, repository/environment identity, secret name, entry/version ID and algorithm version are authenticated for both payload and wrapping, with distinct purpose labels. Rewrapping adds a new immutable key-wrap record; it does not rewrite payload ciphertext or expose plaintext.

Missing/malformed/default keys are errors in every environment; production never falls back to development key material. Rotation retains old KEKs until all referenced versions are rewrapped and a recovery verification is recorded. Recovery restores ciphertext, wrap records and an independently protected KEK backup together.

### Rotation and recovery procedure

1. Provision independent 32-byte random KEKs as unpadded base64url values in the broker-only keyring. Configure distinct base64url signing keys for each service caller.
2. Use a globally scoped `vault.rotate` identity to call `/internal/vault/keys/register` with the registry's `expected_revision` (`0` initially). Key IDs and fingerprints cannot be replaced. Activation fences stale writers at the database boundary.
   Fresh installation may use the idempotent `initializeVaultKeyring` helper / `/internal/vault/keys/initialize` under that same maintenance scope. It initializes only an empty encrypted vault and validates the configured active key on retries; nonempty vaults with a missing registry require recovery. Local setup provisions a separate operator credential, and local startup calls this authenticated operation before starting the UI. A configured KEK by itself is not a registered encryption grant.
3. Run `/internal/vault/keys/rotate` with a stable `rotation_id`, `target_key_id`, and bounded `limit` until complete. Payload ciphertext and tenant value versions stay immutable. Rewrap federation records through the separately scoped `/internal/federation/rewrap` before verification.
4. Run `/internal/vault/keys/recovery` with a stable `verification_id`, `key_id`, and bounded `limit`. The broker fences new ciphertext writes, verifies tenant and federation payload integrity under the replacement key, builds a ciphertext/wrap digest chain, then unfences writes. It returns counts and proof metadata only. Scheduled `sweepVault` resumes both phases. `/internal/vault/keys/abort-recovery` explicitly abandons a failed verification while leaving retirement blocked.
5. Configure `SECRETS_BACKUP_RETENTION_SECONDS` to cover the **actual longest** D1/independent-backup recovery window. Production/staging retirement requires this setting. `/internal/vault/keys/retire` requires replacement wraps, a completed recovery verification covering **both tenant and federation** ciphertext, and the full retention interval **after that verification completed**. An old wrap's creation date is not the backup-retention clock: a backup made immediately before rewrapping can still depend on a years-old wrap. The retirement transaction rechecks the active replacement key/control revision, verification receipt, all tenant wraps and current federation wraps. Removing old provider key material follows this retained-backup window.

Restore exercises must restore the key registry and version/wrap tables with the same independently protected key material, verify recovery before reopening writes, and revalidate/revoke restored identity credentials and execution attempts. Broker authorization never treats a restored or expired attempt as a new grant.

### Policy and API recovery

Runtime release rechecks current principal/credential ancestry, organization SSO, repository policy/epoch, trusted runner-pool ownership, exact frozen selection, current generation/lease, and exact environment approval. Vault and identity rows live at `identityBinding`, never in seeded repository-shard identity copies. Repository and global attempt/webhook/delivery IDs resolve through core authority/locator helpers. The read-only `/internal/vault/authority` protocol returns current metadata snapshots and no tenant values or ciphertext.

Primary SQL witnesses include account authority epochs, membership, grants, role changes, revocation barriers, fork-account dependencies and time-validity predicates. Those snapshots precede runtime metadata checks and are verified in the use-audit transaction after a final current-placement runtime snapshot. The final metadata observation is the grant's authorization point; an unchanged primary witness proves identity/secret policy remained valid through that observation. Generation, approval and runner changes detected by the final snapshot reject the entire response. No value is returned if the primary guard loses a race.

Private broker configuration preserves `IDENTITY_DB`, `IDENTITY_CELL_ID` and `IDENTITY_SHARD_ID` together, plus the current metadata root/shard/cell maps and `DIRECTORY_DB`. Cross-cell reads require `INTERNAL_SERVICE_KEY` only for the fixed metadata authority protocol; it is still not a vault-use credential. Core authorization uses `identityDatabase` / `readRepositoryAuthority` as specified in `docs/routing.md`; the broker fails closed if that decision disagrees with current repository revision/epoch.

Vault writes use their own private, keyed operation fingerprint so low-entropy secret values do not acquire a public/unkeyed password-verification hash in API retry metadata. Retries reauthorize and return current **metadata**, not cached values or prior response bodies. A reauthenticated credential for the same principal can recover an existing operation; it cannot gain use permission from management permission. Normal secret APIs never return ciphertext, wrapped DEKs, KEKs or existing values. Variables remain separately readable configuration.

Values and canonical policies are limited to 16 KiB each. A selection can contain 64 distinct secrets, 128 distinct variables and 128 steps, with a 512 KiB expanded metadata/configuration ceiling. Repeated names do not repeat account-policy authorization queries. Runtime responses allow bounded JSON escaping overhead while remaining transient; the execution caller must not checkpoint them.

## Verification and composition status — 5 October 2026

`tests/high-level/secrets.test.ts` passes **10 consolidated scenarios** covering metadata-only preview/digest parity, scope precedence, write-only management, manage/use separation, immutable ciphertext and identity-context authentication, KEK rewrapping/recovery, purpose-scoped authentication, current generations, authorization-barrier races, exact MFA/credential-bound approvals, both typed runner metadata authorities with primary credentials, lifecycle revocation, and federation. Its retirement regression takes a new backup after the old wrap is already older than the retention interval, verifies both replacement phases, rejects immediate retirement, and permits retirement only after the full new backup window.

`tests/high-level/secrets-workerd.test.ts` passes with the **complete production schema**, bundling the actual private Worker and exercising native Web Crypto/D1 in Miniflare/workerd with Node compatibility. It verifies sealing, immutable rewrapping, stale deployed-writer fencing and both recovery phases. There are no excluded migrations. Together with billing, the owned verification covers 30 passing scenarios.

Private broker routing/identity bindings and the federation identity-contract marker are infrastructure/composition responsibilities. Root TypeScript, the generated API build and the composed secrets Worker bundle pass. The workerd scenario now also verifies explicit first-installation bootstrap, idempotent initialization and refusal to auto-activate a different configured key. No cloud deployment or remote migration was performed.

Checked 4 October 2026 through Context7:

- [Workers Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/) provides native AES-GCM, HMAC and cryptographic randomness without Node compatibility.
- [Workers secret bindings](https://developers.cloudflare.com/workers/configuration/secrets/) are accessible to code in the receiving Worker. Bind KEKs only to this broker.
- [Service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/) isolate private worker-to-worker calls; request authentication and resource policy are additional boundaries.
- [Secrets Store](https://developers.cloudflare.com/secrets-store/integrations/workers/) holds the small platform key set. Tenant ciphertext belongs in D1, not one provider secret per tenant value.
