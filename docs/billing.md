# Billing and cost admission

## Integration contract

`@gitknot/billing` exports `AdmissionController` for the execution Worker's `ADMISSION` binding. Objects are named `account:<account_id>` and `capacity:<slice_id>`; there is no platform-wide admission object. All amounts and metered quantities crossing a boundary are **decimal integer strings**, never JavaScript monetary numbers. One `USD` monetary unit is **10⁻⁹ dollars**. Rates retain an immutable price version, meter version, numerator and denominator. Meter remainder carry is durable; invoice rounding is explicit and occurs only at the payment boundary.

Server functions (snake_case input fields):

- `reserveExecution(env, {account_id, repo_id, run_id, attempt_id, generation, actor_id, workflow_id?, team_id?, executor, profile, maximum_duration_ms, maximum_storage_bytes?, storage_retention_seconds?, maximum_egress_bytes?})` returns a durable reservation or a fair-queue ticket. The whole-job maximum includes allocation, checkout, execution, snapshot/log drain and destruction. `maximum_duration_ms` is an integer; quantities/amounts are strings. `executor` is `hosted` or `self_hosted`.
- `previewExecutionQuote(env: BillingBindings, input: PreviewExecutionInput): Promise<ExecutionQuotePreview>` is the read-only compiler/UI form. `PreviewExecutionInput` is `ReserveExecutionInput` without `run_id`, `attempt_id` or `generation`. It shares execution's current plan/entitlement validation, authority reads, prices, retention/grace and per-object headroom math. It returns the quote cost/rate fields, `payer_account_id`, subscription/plan revisions, repository revision, null runtime attribution, and `availability: {state:'eligible'|'unavailable', admission_required:true, reasons:[{code,message}]}`. Eligibility describes the observed configuration; spend, quota and concurrency admission still happen when execution starts. An uninitialized billing account receives its initial Free-plan price terms with an unavailable/setup reason. Preview performs SELECTs only: account setup, credits, fee holds and admission-controller calls are outside this path.

  Missing preview prices/plans use typed `price_unavailable` / `plan_unavailable` errors; unavailable billing storage uses `billing_preview_unavailable`. Compiler/UI callers preserve those as blocked diagnostics with unknown cost. A pricing failure never produces a zero-price fallback. Exact route-owner contracts are also recorded in `docs/execution.md`.
- **Before allocation**, `startExecution(env, {account_id, reservation_id, fence, runtime_id})` obtains the one fenced allocation grant. Use a deterministic runtime/allocation ID and attach to it on retries. A reservation by itself is not permission to allocate.
- `settleExecution(env, {account_id, reservation_id, fence, event_id, runtime_id, duration_ms, egress_bytes?, termination_proof, outcome})` settles once. `termination_proof` records an authoritative teardown/never-started receipt, not lease expiry. An uncertain or unreachable runtime keeps its financial and capacity holds. Infrastructure-failure refunds are explicit ledger entries and do not refund platform operating cost.
- `cancelExecutionReservation(env, {account_id, reservation_id, fence})` only releases a reservation that has never issued an allocation grant. Once started, cancellation requests teardown; settlement requires termination evidence.
- `reserveStorageObject`, `commitStorageObject`, `accrueStorage`, and `deleteStorageObject` account for immutable R2 objects, byte-time, retention and verified physical deletion. Integrate uploads **before** accepting bytes, enforce the returned byte cap while streaming, and complete the upload before deletion can release its quota. Execution settlement does not release retained-object commitments.
- `sweepBilling(env)` retries financial projections and cleanup/accrual. It never treats a deadline as evidence that external work stopped.
- `previewSeatChange(env, {account_id, additional_seats})` returns the seat delta and exact cost before invitation acceptance. Membership acceptance must consume a valid seat reservation; details below.

`DB`, `ADMISSION`, `BLOBS`, `BACKUPS`, `CELL_ID`, and `INTERNAL_SERVICE_KEY` are required shared bindings. `BILLING_PLATFORM_SLICE_ID` selects the cell's preallocated cost/capacity slice. Optional card collection uses a private `PAYMENTS` service binding and its own signed scope; absence means manual invoicing, not simulated payment success. Platform slices and immutable price/plan versions are provisioned in D1 before admission is enabled. Missing, stale, stopped or unreconciled admission state fails closed.

The account coordinator atomically holds all applicable account/repository/team/workflow/actor budgets plus quota and tenant concurrency. It then prepares and commits its capacity slice using a durable fenced saga. Compensation only releases an unstarted reservation, and tombstones prevent delayed prepare/commit requests from reviving it. Failed or ambiguous remote calls retain holds until reconciled. Fixed slice allocations plus baseline storage/service commitments fit the platform pool cap; slices cannot independently manufacture budget.

Public routes are registered with `registerBillingRoutes(app)`: `/v1/accounts/:accountId/billing`, `/usage`, `/budgets`, `/invoices`, `/statements`, `/subscription`, and `/credits`. Accounts may be personal or organizations. Billing permission is independent of repository content permission. Budget amounts describe gross metered cost; credits reduce the payable balance and do not create operating-cost headroom.

## Provider boundaries

Checked 4 October 2026 using Context7 and official documentation:

- [D1 batches](https://developers.cloudflare.com/d1/worker-api/d1-database/) are transactions and roll back on a failing statement. Financial publication uses idempotent, constraint-guarded batches.
- [D1 Sessions](https://developers.cloudflare.com/d1/best-practices/read-replication/) supply sequential consistency. Authorization and fresh configuration use primary reads.
- [Durable Object concurrency](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/) permits interleaving around non-storage I/O. Budget changes use storage transactions; remote participants are never assumed to share a transaction.

## Ledger and commercial policy

Runner time is measured in integer milliseconds, including allocated startup and teardown. Queue/approval waiting has no runner charge. Storage uses decimal bytes and a fixed 30-day GB-month (`2,592,000,000,000,000,000` byte-milliseconds per unit). Rates and plans are immutable records; new pricing requires a new version. Included credits reduce invoices rather than increasing operating-cost capacity.

Each account has durable meter remainders. A retained object's fractional carry stays with that object and is merged into account carry when the object is deleted or its ownership segment closes. Infrastructure-failure refunds and execution/retention overrun waivers restore the unbillable portion's fractional carry as well as its monetary amount. A delayed provider cleanup therefore does not charge a customer beyond its admitted execution quantity or financed storage window; platform metering still records actual consumption and stops further admission on an overrun.

Subscription and seat proration uses exact integer numerators over a denominator divisible by every calendar month's length. A period closes only after prior attempts settle and retained objects are accrued through its boundary. Payment rounding happens once per invoice; signed sub-cent carry is retained for subsequent statements, including zero-due invoices. Statements include usage, subscription lines, credit applications and payment-rounding adjustments. Standing subscription/seat peak commitments remain held through period close; abandoned reservations do not themselves create invoice charges.

Initial account admission reserves its active recurring fee and seats. Period rollover settles the old fee, carries outstanding storage/runtime exposure, and reserves the next period's active subscription and accepted/pending seats **in one account-DO transaction** before reopening admission. A lost rollover acknowledgment cannot expose a zero-commitment window for lowering the cap.

`billing_usage_rollups` stores independent cumulative contributions keyed by `coordinator_id`; local revisions never overwrite another capacity slice. `usageRollups(db, {account_id,period,dimension,operating_cost?,after?,limit?})` groups those contributions with exact BigInt addition and returns decimal-string totals. Public usage/forecast and invoice reads use this aggregation; SQLite numeric `SUM` is not used for money.

`previewSeatChange` returns `subscription_revision`, `monthly_delta_units`, `maximum_current_period_units`, and the resulting seat count. `reserveSeatChange` accepts `{account_id, principal_id, additional_seats, request_id, expected_revision}`. Its `request_id` must be stable. Include the result of `seatAcceptanceStatements(db, {account_id, principal_id, reservation_id})` in **the same guarded D1 batch** as membership/provisioning acceptance. A failed batch leaves the seat unconsumed; `cancelSeatReservation` only cancels a reserved seat. SCIM/JIT use this same contract. Human seat removal closes/opens a plan segment in its membership transaction.

## Public request recovery

Public budget, stop-control, plan-change, seat-reservation, credit-redemption and payment requests explicitly use core external recovery. Their stable identity is `c.get('idempotency').operation_id`. `billing_api_operations` commits a sanitized intent with core `mutationStatements` before external work. Account-DO budget/stop command receipts share the same storage transaction as their effects. Retries reconcile that command or the original subscription/seat/credit journal and return the current authorized resource; they do not reapply an earlier edit. Operation records contain references, never cached response bodies or historical HTTP errors. Gift-code inputs are stored only as hashes.

API cells must retain the core `IDENTITY_KEYS_JSON` versions used for keyed request fingerprints throughout the retry window. Missing historical fingerprint keys fail closed rather than issuing another billing operation.

Subscription settings and seat cancellation use a single core `mutate` batch, including their revision guard, source event, audit and generation-fenced request receipt. Billing code does not write `idempotency_keys` directly. `GET /v1/accounts/:accountId/billing/operations/:operationId` exposes safe operation metadata.

## Optional payment adapter

`PAYMENTS` is a private service binding; `PAYMENTS_SERVICE_KEY` is a distinct random signing secret, separate from the general internal key. `/internal/payments/collect` receives the immutable invoice ID as its idempotency key, USD and **decimal-string cents**. The adapter must retain its invoice-to-processor mapping and enforce idempotent collection. An acknowledged submission is not a claim that payment settled.

After independently verifying a processor notification, the adapter signs `POST /internal/billing/payment-settlement` with scope `billing.settlement` and `{account_id, invoice_id, processor_event_id, payment_id, amount_cents, occurred_at}`. The amount, current invoice and event identity are checked and the paid state/audit/event commit atomically. Request recovery never issues another collection after a durable dispatch marker; it waits for the authenticated settlement. Without the adapter, invoices use manual collection and a collection request fails explicitly.

## Operating allocations and maintenance

Provision `billing_platform_pools` with an explicit cap, safety buffer, base-service/storage commitments, admission window and instance ceiling. `allocatePlatformSlices` atomically allocates immutable cell slices against those totals using the pool revision. There is no automatic production allocation or global admission DO. Every execution cell selects a funded slice with `BILLING_PLATFORM_SLICE_ID`; omitted or unavailable allocations stop new work.

Normal local setup invokes the same allocator in workerd after applying local migrations. Its development-only `initial-v1` pool has a 25 USD cap, 1 USD safety buffer and 1 USD baseline commitment; the default discretionary slice has a 10 USD allowance, two instance slots, 2,000,000,000 storage bytes and a fixed 30-day admission window. Separate configured Git-storage and essential slices retain their respective purposes. Setup and E2E capacity use the shared helper, which preserves existing allocations, holds, stop controls, admission epochs and expiry. `--inspect` is read-only; a new `--generation` requires unused configured slice IDs for new funding and never reparents or renews an existing slice. See [finite local operating allocation](./setup.md#finite-local-operating-allocation).

`setPlatformStop` fences pool admission first, then all initialized slice controllers. Per-account controls retain running holds. Admission alarms retry financial journals; `sweepBilling` accrues/renews storage, reconciles invoice/plan finalization, emits threshold events and marks overdue accounts. Partial maintenance failures are reported for a bounded retry. Cleanup uses recorded physical storage placement and remains available when spend admission is stopped. R2 snapshot storage uses the execution worker's `BACKUP_BUCKET`, separately from general `BACKUPS`.

### Periodic storage checkpoints

`LIMITS_JSON.billing_storage.periodic_accrual_seconds` defaults to **3,600 seconds**, with an explicit operator range of 60–3,600 seconds. Billing and the existing Operations manifest-accrual caller use the same completed UTC time bucket. A resource normally publishes at most one periodic accrual per checkpoint; overlapping sweeps reuse that exact timestamp, which the existing transactional meter makes idempotent. Unchanged sweep cursors and not-yet-due expiry requests produce no per-object writes or admission calls. Page limits remain 64 storage objects and 32 canonical meters per billing pass.

This coalesces observation frequency, not usage. The meter keeps the original `accrued_at` until it records the full intervening byte-time with the same owner, immutable price and rational carry. Explicit accrual, native publication, verified deletion/purge, owner/physical cutover and retention renewal retain their exact timestamps. Due funded/retention/commitment boundaries, invoice month boundaries and canonical peak-day boundaries bypass the ordinary cadence. Cleanup and unknown-upload/publication holds retain their existing checks. Admission still reserves the full funded interval: converting an amount from commitment to settled usage leaves `settled + reserved + commitment` unchanged, so uncheckpointed funded usage creates no new budget headroom.

The final manual soak exposed 10,385 storage and 191 Git periodic events in about 53 minutes; **all 10,576 settled zero nano-USD**. Storage alone wrote 20,770 zero-charge ledger rows across account and capacity while updating fractional carry. The 55 objects occupied only 79,728 bytes, and the populated Git meter held 1,468 logical bytes. There was one publication attempt per event; 46 consumer jobs had a second attempt, which does not explain the unique-event volume. The saved read-only analysis and exact counts are in `dogfood-output/background-accrual-cost-analysis.json`.

There is no per-event D1/Queues/Worker/DO overhead debit in the billing price catalog. That shared overhead relies on the operator's baseline commitment and safety headroom; the previous sweep rate was not an accurately priced platform-cost bound. For 55 objects and one canonical meter, one dispatcher plus five consumer messages implies 18 queue operations per event before retries. At [published Queues marginal pricing](https://developers.cloudflare.com/queues/platform/pricing/), the former 60-second production cadence models **17.41824 USD per 30 days for Queues alone**, versus **0.290304 USD** at hourly checkpoints, excluding shared included allowances and mandatory lifecycle events. The 15-second local cadence models 69.67296 USD. These are workload estimates, not local provider charges; [D1 row/index writes](https://developers.cloudflare.com/d1/platform/pricing/) and runtime costs are additional and must remain covered by the operator's explicit baseline.

The final periodic-metering gate passed **46/46 tests across four files** (`billing`, `billing-placement`, `events-recovery`, `events-movement`), and root TypeScript passed. One high-level regression runs 55 stored objects and a canonical meter through 212 fifteen-second ticks, including concurrent billing/Operations sweeps: exactly 56 periodic outbox events and 112 ledger rows, zero SQL row changes before the first checkpoint, and fewer than 2,000 SQL row changes over the run. It verifies closed-form final money, byte-time and fractional carry for both owners and capacity through a non-checkpoint cutover, failed/confirmed deletion and Git purge. It also preserves an unknown upload hold, rejects admission without commitment headroom, emits a due retention request before the next checkpoint and verifies terminal replay adds no ledger rows.

## Standalone storage contract (API / lifecycle integration)

```ts
reserveStandaloneStorage(env, {
  account_id, repo_id: string | null, actor_id, object_id, key,
  bucket: 'blobs' | 'backups', maximum_bytes: string,
  retention_until: string | null,
}): Promise<StorageObject>
```

The result includes `reservation_id`, `fence`, `source: 'standalone'`, `admission_state: 'ready'`, the immutable price, maximum bytes, financed lifetime, and renewal policy. It has no run/attempt and occupies no compute slot. The account Durable Object is the single monetary and byte-quota authority for all repository shards; repository byte caps are also applied there. The caller must authorize `attachments.write`, `accounts.manage` for account assets, or its specific backup/import capability before admission and again before accepting/publishing bytes. Admission alone grants no content permission.

Keys use `${account_id}/${repo_id ?? 'assets'}/…`. Persist the returned reservation and fence in the manifest before changing `reserving` to `pending`. `commitStorageObject(env, {account_id, reservation_id, fence, object_id, bytes, etag, checksum})` verifies the actual R2 head and commits both account and operating-cost holds. SHA-256 accepts canonical hex or a `sha256:` prefix. The uploader must enforce the exact length/checksum and use an immutable R2 write.

`deleteStorageObject(env, {account_id, object_id})` owns **physical deletion and financial settlement only**. It does not change `object_manifests`, associations, feature quota mirrors, or feature history/outbox records. The feature owner must fence and finalize those in its own guarded transaction exactly once. The former raw `updateRetentionManifest` helper is removed.

For unused intents use `cancelStandaloneStorageIntent(env, {account_id, object_id, repo_id?})`. It reads the immutable locator and current primary manifest, which must already be fenced as `deleting`, unreferenced, and have either `upload_generation === 0` or the verified `upload_failure === 'input_incomplete'` marker. It installs a permanent account-DO tombstone before compensating, including when admission failed before any meter/reservation was created. A late prepare or admission cannot revive it. The result is `{id,account_id,repo_id,key,bucket,source:'standalone',state:'cancelled',reservation_id:string|null,fence:string|null}`; nulls mean no financial reservation ever existed. A zero received-byte counter alone is never proof. Unknown upstream acceptance remains held/fenced. An existing metered unused upload can also use the verified `abortStandaloneStorage` path.

The billing layer accepts authorized backup/restore retention for an existing tombstoned repository whose owner still matches. It grants no read, upload or publication permission; the caller's lifecycle/attachment authorization and manifest fences remain mandatory.

`retention_until: null` requests continuing retention with **renewable cost commitments**, not a hidden object TTL. `LIMITS_JSON.billing_storage` configures `commitment_seconds` (default 30 days), `renew_before_seconds` (7 days), `deletion_grace_seconds` (14 days), `maximum_retention_seconds` (3,650 days for explicitly finite retention), and `maximum_objects` (100,000). `renewStorageCommitment` and `sweepBilling` renew before the financed window ends. Insufficient funding produces an auditable `billing.storage.funding_required` event, blocks new discretionary work, and exposes `delete_after` at the already-financed grace boundary. Successful renewal clears that notice and cancels an unclaimed older deletion request. The initial reservation includes the entire grace cost. [R2 storage continues to be charged while data is retained](https://developers.cloudflare.com/r2/pricing/).

Automatic expiry emits a durable `billing.storage.deletion_requested` event and `billing_storage_deletion_requests` row; it performs no feature or physical deletion itself. The owning generic-upload, collaboration, archive, LFS, or execution handler consumes that event. `storageDeletionRequests(env, {account_id?,after?,limit?})` provides bounded recovery listing. The owner calls `claimStorageDeletion(env,{account_id,object_id,request_id})` before its own fence, then `deleteStorageObject`, then its own manifest/association/quota/history finalization in the consumer's idempotent transaction. A changed funding/ownership generation rejects the claim. `releaseStorageDeletionClaim` is allowed only before billing has durably recorded that physical deletion may have started. The request's `financially_deleted` state is not a feature-finalization receipt; replay the original feature consumer until its own receipt commits.

Deletion-request uniqueness applies only to live `pending`/`claimed` rows. Releasing a claim preserves its cancelled history, and re-expiry can issue a fresh request for the same deadline without poisoning the financial journal. Claim/release retries are idempotent; replaying an old release cannot cancel a newer request.

Repository metadata and manifest checks use primary shard routing. Account-only manifests use the account authority. Cross-cell metadata calls use the signed `billing.metadata` private API endpoint; billing never makes an independent account quota in a repository shard.

### Prospective ownership handoff

Lifecycle uses three resumable server functions, with the repository fenced and execution/uploaders drained:

1. `prepareRepositoryStorageTransfer(env, {operation_id, repo_id, from_account_id, to_account_id, actor_id})` verifies an accepted `repository_transfers` row, fences old-owner accrual, and reserves the receiver's quota/cost plus platform cost for every retained object. Partial prepares retain both sides' holds until reconciled.
2. Perform the repository owner CAS while keeping writes fenced. Record its UTC `effective_at`.
3. `commitRepositoryStorageTransfer(env, {operation_id, effective_at})` verifies the accepted destination is now the owner, meters the old owner exactly through that boundary, activates the receiver's metering at that same boundary, and updates the storage ownership receipts. Historical ledger rows are immutable. Unfence publication after this finishes.

If the catalog transfer is cancelled before its owner CAS, `abortRepositoryStorageTransfer(env, {operation_id})` verifies that cancellation/old ownership and compensates prepared receiver holds. There is no expiry-based handoff or release. Completed per-object receipts are retained for updating `object_manifests.billing_reservation_id` / `billing_fence`; callers also keep manifests fenced until they point to the committed owner.

Preparation/commit/abort are bounded to 32 objects per call; repeat durable Workflow steps until `prepared`, `complete`, or `aborted`. `actor_id` is the accepting principal from the authoritative transfer row. Read completed receipts with `storageTransferReceipts(env, operation_id, cursor?, limit?)` in a separate resumable phase, apply them to manifests, then unfence the catalog. This avoids losing receipt updates if a response/checkpoint is lost.

The cell-local API mounts signed `billing.metadata` and `billing.physical` handlers for current-placement metadata and physical R2 observations. Identity/financial reads use `identityBinding`; repository authority uses the core routing protocol rather than seeded source copies. Cross-cell calls use configured `CELL_BINDINGS_JSON`; missing placement bindings fail closed. The recorded physical cell is retained through owner changes. A cell handling `snapshots` physical operations must bind its snapshot bucket or mount `handleBillingPhysicalRequest` on its private execution service.

### Same-owner physical placement

The five `*RepositoryStoragePlacement` helpers and their exact phase order are documented in `docs/lifecycle.md`. Migration `077_billing_storage_placement.sql` stores immutable placement identities, one-writer copy generations, scratch/canonical commitments and cleanup receipts. Temporary physical duplicates occupy real account/repository and destination-slice quota before bytes are accepted. The logical payer and object/upload identities remain stable; `storage_cell_id`, `storage_epoch` and `platform_object_id` switch together at the fixed effective timestamp. Overlap is provider consumption, while customer logical byte-time switches once. Original-cell deletion is verified before its quota/cost hold is released.

The API mounts purpose-authenticated `/internal/billing/placement/:action` for fixed physical operations and `/internal/billing/admission` for bounded one-hop coordinator routing. Account homes are recorded in identity-owned `billing_controls.body_json.coordinator_cell_id`; capacity homes come from the identity-owned slice record. Explicit authority descriptors travel with database bindings, and routing never creates a billing copy in a repository shard. Isolated runtime test/delegate environments retain only their required identity routing row and the authoritative `ADMISSION` binding. Normal uploads after movement select the actual physical cell's slice.

Ops owns metadata/inventory/audience verification and finalization, and consumes the financial receipts through its current move workflow. Git's private physical endpoint and funded scratch/provision hooks are integrated into the native restore path. `sweepBilling` retries durable financial switch/cleanup/abort decisions; unresolved external writes retain their holds and fences.

Migration `102_billing_placement_safety.sql` retains exclusive namespace grants, creation evidence, native terminal-publication receipts and physical cleanup outcomes. `placementStorageName(repoId, operationId)` hashes both complete, case-preserving identities with full SHA-256. A grant follows a real absent observation, fixes an unpredictable operation/target-bound marker before creation, and permits exactly one create-only request. `placementGitProvisionMarker` returns that original marker. `confirmPlacementGitProvision` accepts only `{version:1,provider:'local'|'artifacts',storage_name,provider_id,marker}` from actual creation-bound provider evidence; the marker/name must match the grant and the first provider ID is immutable. An existence probe cannot establish ownership.

Artifacts receives the reserved marker only as the documented create-time `description`, and recovery reads fresh `info()`/REST metadata. The local authority writes and fsyncs an exclusive creation receipt after successful mkdir/Git initialization. A lost successful reply is recoverable when this matching provider evidence exists. A lost create rejection, missing marker, conflicting provider ID, timeout or unknown response retains the original grant, scratch, financial holds and lifecycle fences. Only a delivered, conclusive create-only `not_started` rejection can record the unused-allocation tombstone; a foreign namespace is never deleted. The provider metadata contract is documented, while actual Artifacts create/metadata atomicity remains part of deployment acceptance: [Workers binding](https://developers.cloudflare.com/artifacts/api/workers-binding/), [REST](https://developers.cloudflare.com/artifacts/api/rest-api/).

Rollback closes every discovered account/source/destination participant before compensation. Acquisitions compare the immutable placement generation and closed tombstone inside the same admission transaction, including requests that captured an older D1 placement before abort. Before any rollback deletion, native reconciliation must return and persist a strict `PlacementPublicationFence` with the exact operation/repository/store/fence/epochs, a real terminal state, `finalized:true` and `writer_fenced:true`; creation ownership must also be confirmed. Pending native publication never becomes a synthetic financial rejection. Namespace cleanup distinguishes an owned, verified deletion from positively unallocated work.

Ordinary same-cell shard movement retains canonical Git and physical buckets. An explicit archive recovery is the immutable `archive_restore` purpose even within the same cell: it selects a fresh namespace and funded Git slice, reserves the receiver's enforced inflated-graph/object-framing bound, and separately finances scratch using the verified manifest's exact bundle bytes. Compressed bundle size and the current live graph are not substituted for the historical graph's admission bound. Final native verification compares the target refs to that immutable archive inventory; logical customer consumption still switches only at the single effective timestamp.

## Native Git helper and canonical storage admission

All six functions in the [Git adapter contract](./git.md#billing-adapter-coordination-5-october) are exported and used by the Git adapter:

- `reserveEssentialService` finances the helper's full declared lifetime, egress ceiling and initiating-operation allowance before allocation. `startEssentialService` issues its fenced startup grant. `settleEssentialService` requires the exact authenticated destroyed-generation receipt, or a provably unstarted reservation with zero usage. Uncertain startup/teardown keeps both cost and capacity holds.
- `reserveCanonicalGitStorage` prepares account/repository/actor caps, accumulated retained-growth quota and the platform storage slice. `commitCanonicalGitStorage` verifies the authoritative Git publication/marker and exact object/ref evidence. `abortCanonicalGitStorage` requires a definitive rejection and tombstones lost-reply intents even when no reservation ID was received. An explicit unstarted rejection releases unused admission; an upstream report-status rejection retains a conservative bound for potentially retained provider pack bytes.

### Essential reads, exports and helpers

Provision a separate platform pool with `purpose='essential'`, including an explicit baseline commitment and safety buffer, then use `allocatePlatformSlices` to create its essential slices. The allocator preserves the pool purpose and checks the sum of allocations, baseline and safety against the real pool cap. Configure `BILLING_ESSENTIAL_SLICE_ID` on Git callers. Customer CI and canonical storage use discretionary slices; customer stops cannot spend or disable essential read/export/reconciliation capacity. Allocation purpose belongs to the base billing catalog migration `060`; Git meter/profile tables are in `076`.

The immutable `standard-2` profile describes 1 vCPU, 6 GiB memory and 12 GB disk, with a maximum 330-second episode. Its v1 operating bound is 40,000 nano-USD per second (10 ms upward ticks), covering full-profile CPU, memory and disk from allocation through teardown. Egress is bounded at 50,000,000 nano-USD per decimal GB. `GIT_HELPER_OPERATIONS` defaults to 1,024 and is capped by the immutable profile; the full declared allowance is funded and settled at 150,000 nano-USD per initiating operation. Each intent freezes that configuration and all price versions, so configuration changes cannot alter a retry. These are explicitly named operating-cost bounds, including protocol allowances and without subtracting provider free tiers; they are not fabricated provider CPU or invoice measurements.

Helper ledger entries use `git.helper.standard-2`, `git.helper.egress`, and `git.helper.operations`, separately from customer workflow compute. Helpers have no fake run/attempt or account compute slot. The helper controller supplies real wall-time and durable egress observations, and freezes settlement before releasing its generation. Billing independently rejects understated lifetime, duplicate event reuse, changed receipts and never-allocated claims after startup.

### Logical byte-time and retained provider exposure

`BILLING_GIT_STORAGE_SLICE_ID` selects canonical storage's discretionary platform slice; it defaults to `BILLING_PLATFORM_SLICE_ID`. Customer v1 metering is **logical reachable Git object byte-time** from verified native graph observations, including retained refs and excluding internal transaction-marker metadata. Monetary arithmetic uses the same rational byte-millisecond carry as other storage, with immutable `git.storage.logical` prices. The v1 customer price is 500,000,000 nano-USD per decimal 30-day GB-month. A confirmed publication establishes the next logical-byte observation; receipts preserve the observation boundary across retries.

Platform `git.storage.daily-peak-bound` accounts for conservative retained growth in byte-days at 500,000,000 nano-USD per 30,000,000,000 byte-days. Each newly exposed day is financed, including the current day's peak when purge happens later that day. Calendar segments preserve month attribution and exact fractional carry. Ref deletion reduces subsequent customer logical consumption but never releases accumulated retained-growth quota or provider commitments. No physical Artifacts byte measurement is inferred from compressed packs or `info()` metadata.

`retention_until:null` uses the disclosed rolling funding/grace policy. `sweepBilling` accrues and renews canonical meters through account/slice prepare/commit decisions, with durable compensation only before a commit decision. Funding failure emits `billing.git.storage.funding_required`, including the financed grace boundary, and stops discretionary admission. It preserves essential reads/export and retained exposure while lifecycle cleanup is pending. The lifecycle owner handles canonical repository retention; billing never silently removes refs or changes repository state.

Verified Operations `purge-storage` receipts, paired with their `fence-writes` snapshot of the exact storage name, are consumed by maintenance to settle canonical purge. The proof is frozen in `billing_git_purges` before either financial participant releases quota. Physical uncertainty or a mere catalog deletion never releases it. Existing `prepareRepositoryStorageTransfer`/`commitRepositoryStorageTransfer`/`abortRepositoryStorageTransfer` also include canonical meters: receiver funding precedes the owner CAS, both ledgers use its identical boundary, and platform physical quota is handed over exactly once.
